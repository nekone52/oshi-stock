# 推しストック（oshi-stock）

## 1. サービス概要

**このサービスはどんなサービスか**
予約から支払い・発送までの期間が長いグッズに特化し、URLや画像から直感的に登録して発売順に自動整理・一元管理できるWebサービス。

**誰の、どんな課題を、どう解決するか**
メモ帳での文字管理が面倒で二重買いや支払い忘れを繰り返してしまうオタク層が、キャラ別の視覚的なUIで必要個数・在庫数・ステータス（未払い/支払済）を個別アカウントで安全に管理し、安心して推し活を楽しめるようにする。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- **いつ**: アニメイト等の通販サイトで推しの限定グッズや受注生産商品を予約したとき。
- **どんな状況で**: アニメイト通販などは注文時ではなく「商品在庫が確保された段階」で後から支払い手続きが発生するため、数ヶ月後に突然支払い案内が届く。複数の通販サイトを併用していると「どれが支払い済みで、どれが未払いか」「いつ発売されるか」が分からなくなる。標準のメモ帳に記録しようとしても、文字だけの無機質なメモは開くやる気すら起きず、結局放置して同じグッズを重複して買って（二重買いして）しまうことが何度もあった。
- **どんな気持ちになったか**: 届いた荷物を開けて二重買いに気づいたときのショックと自己嫌悪。また、支払いを忘れて自動キャンセルにならないかという焦りがあり、推し活なのに事務処理のストレスで純粋に楽しめなくなっていた。

### 2-2. なぜそれが「気になった」のか

グッズ管理が苦手な自分にとって、「ただ文字を並べるだけのメモ帳やスプレッドシート」は作業感・義務感が強すぎて続けられないため。推しを愛でるテンションのまま、視覚的・直感的に「開くだけでテンションが上がって触りたくなる場所」でなければ、自分のようなタイプのオタクは続けられないと痛感したため。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

通販サイトごとに異なる発売時期や支払いタイミング（確保後支払いなど）が把握できず、グッズの重複購入（二重買い）や支払い忘れが発生する。

### 3-2. 本当に解決したい課題は何か

- **なぜ？（1回目）**: メモ帳やスプレッドシートでの記録はやる気が出ず、管理を後回しにして何を注文したか忘れてしまうから。
- **なぜ？（2回目）**: アニメイト等では「在庫確保後の後払い」というタイムラグがあり、即時決済と混ざって「支払い済みか」「届く予定があるか」がメール検索でも追えなくなるから。
- **なぜ？（3回目）**: 画像やURLのない文字だけのメモでは「どの絵柄のグッズか」がパッと直感的に思い出せず、販売時期順にも並ばないため、通販サイトの画面前で再確認するのが面倒になって衝動買いしてしまうから。

**本当に解決したい課題**: 無機質な管理ツールの作業感にやる気を削がれ、重複買いや支払い漏れによる自己嫌悪を繰り返してしまい、純粋な気持ちで推し活を楽しめなくなること。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| 年齢 | 20代〜30代 | 自分で自由に使える収入があり、受注生産やアニメイト等の通販予約、イベント物販を頻繁に利用し、グッズの購入頻度が高い年代であるため。 |
| 生活・状況 | 日常的に複数の通販（アニメイト、公式EC等）を利用し、数ヶ月先のグッズを日常的に予約しているが、事務的な細かいタスク管理は苦手。 | 支払いタイミングのズレや発送のタイムラグが頻発し、記憶やメモ帳だけでは注文状況を維持できず重複買いを起こしやすいため。 |
| 環境 | 主に外出先やベッドの中で、スマホからグッズ情報を巡回・購入する。 | PCを開いてわざわざ表計算ソフトを起動する気力がないため、スマホのWebブラウザからワンタップで視覚的に記録・確認できる仕組みが必要。 |

### 4-2. 自分とユーザーの距離

**自分自身。** 実際に自分自身がグッズ管理が苦手で、メモ帳をつけるやる気が出ずに二重買いを何度も経験し、アニメイトの在庫確保後支払いに頭を悩ませている当事者であるため。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- **まず最初に使ってくれそうな人**: 自分自身、および同じように通販で二重買いをやらかした経験があるオタク仲間。
- **どんな場面でこのアプリを思い出すか**: X（旧Twitter）で新作グッズの予約情報を見たとき、通販でポチった直後、イベント物販列に並んでいるとき。
- **今の生活の中で代わりに使っているもの**: スマホの標準メモ帳、注文完了メールの検索、スプレッドシート。
- **それを置き換えてまで使う理由はあるか**: メモ帳では文字ばかりでやる気が出ず続かないが、本サービスなら推しのアイコンやカラーで彩られた画面に画像やURLを貼るだけで、販売順に自動整頓され、楽しく直感的に二重買いを防げるから。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ

- **きっかけ**: またしてもグッズを二重買いしてしまい、「文字メモ以外の、視覚的でやる気の出る管理方法はないか」と悩んだとき。
- **最初の一歩（登録・導入）**: 個別アカウントを作成（メールアドレス・パスワード認証）後、推しの名前・アイコン画像・推し色（厳選24色プリセット）を設定する。スマホ画面風の推しアイコンが生成され、一気に自分専用の推し部屋ができる。
- **利用を続ける理由**: 無機質なデータ入力ではなく、『ペルソナ』風のスタイリッシュなUIと推し色テーマの中で、画像・URL付きのコレクションが発売順に並んでいく視覚的快感があるため、管理作業そのものが苦にならず続けられる。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- **サービス名**: 一般的なコレクション管理・家計簿アプリ
- **URL**: （既存アプリ等の参考URL）
- **できること**: アイテム名と金額を入力して出費を記録する、または所持しているグッズの点数をテキストや一覧表で記録する。

### 5-2. それでも自分が作りたい理由

既存ツールは「買った後の金額」や「手元にあるモノ」の事務的な記録が主で、アニメイトのような「後から在庫確保通知が来て支払いが発生する」というオタク特有のタイムラグ（未払いチェック）に対応していない。また、発売順の自動整頓やキャラ別の一括操作がなく、画面も無機質なため、メモ帳と同じように放置して二重買いを繰り返してしまう点に強い不満があった。

### 5-3. 差別化を「体験価値」で表現する

「やる気の出ない事務的な文字入力作業から脱却し、『ペルソナ』シリーズのような滑らかでスタイリッシュなUIと推し色テーマの中で、URLや画像を貼るだけで発売順に自動整理され、キャラ別に『未払い・手持ち在庫・目標個数』を直感的に把握して二重買いの自己嫌悪から解放される体験」。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- **行動の変化**: メール検索やメモ帳を放置しなくなり、グッズ情報を得た瞬間にURLを貼って欲しいものチェックし、発売順に整理する習慣がつく。
- **気持ちの変化**: 「また重複して買っちゃった…」という自己嫌悪や、支払い漏れの不安がなくなり、安心して推し活を楽しめる。
- **考え方の変化**: グッズ管理が「面倒な義務」から「推しのコレクションを視覚的に積み上げていく楽しい遊び」に変わる。

### 6-2. 価値を一文で表す

「このサービスはメモ帳でのグッズ管理が苦手で二重買いを繰り返してしまう推し活ユーザーが、URLや画像を使って発売順・キャラ別に在庫や支払いを可視化し、買い逃しや重複購入の不安から解放されるサービス」

## 7. このアプリで実現すること

### MVPで作る機能

1. **ユーザー認証・個別データ管理**
   - 会員登録、ログイン、ログアウト機能（個別ユーザーごとのデータ完全分離）
   - ※Rails 8標準認証ジェネレータを活用してシンプルかつ堅牢に実装

2. **推しキャラクター & テーマ設定**
   - キャラクター登録（名前、アイコン画像 / Active Storage + S3）
   - 厳選24色テーマ切り替え: 視認性とコントラストを担保した24色プリセットから推し色を選択。Tailwind CSSのカスタムプロパティで全体のアクセントカラーが連動。

3. **スマホアプリアイコン風ホーム画面**
   - スマホの画面のように推しアイコンが並ぶスタイリッシュなダッシュボードUI
   - Stimulusによるアイコンタップ演出: タップ時にアイコンがポヨンと弾むマイクロインタラクションとともに、キャラ別グッズ一覧へ滑らかに遷移

4. **グッズ登録・管理機能**
   - グッズ名、商品画像（1枚）、販売情報の参考URL貼り付け
   - 発売予定日（年月日または年月）の入力と、発売日順（昇順/降順）の自動ソート一覧表示
   - 目標個数と現在確保数（例: 痛バ用缶バッジ 12/24個）
   - 画面遷移なしのステータス更新（Turbo + Stimulus）: チェックボックス（「欲しいものチェック」「予約中（未払い）」「支払い完了」「自宅確保」）を押した際、画面リロードを挟まず「シュッ」とアニメーションしながら即時更新

5. **キャラ別カテゴリ整理 & 一括削除**
   - キャラクター別のタブ切り替え・絞り込み
   - 一括削除モード（Stimulus演出）: 編集/削除モードに切り替えると、スマホのようにアイコンやカードがプルプル震える視覚効果を表示し、チェックを入れたアイテムを一括削除

6. **フィルター表示**
   - 「未払い」「今月発売予定」などのワンタップ絞り込み

### 本リリースで作る機能

- **URL貼り付けによるOGP（画像・タイトル）自動取得**
  公式通販やSNSのURLを貼るだけで商品情報を自動補完。※OGPタグが存在しないサイトや取得失敗時に備え、スムーズに手動入力フォームへ切り替わるフォールバックUIを実装。
- **複数グッズの一括登録機能**
- **グッズ交換・譲渡メモ機能（個人情報非保持・非営利メモ）**
  - 【出】自分が送るアイテム / 【求】相手から受け取るアイテムの送受ステータス管理
  - 取引相手の個人情報（本名・住所・口座等）は一切入力させず、SNSアカウント名（@ID等）と進捗のみを管理
  - ※業としての物品売買・仲介は行わず、あくまでユーザー個人のメモ帳機能として提供する旨を規約に明記
- **カレンダー形式での発売月・発送予定一覧表示**

## 8. このアプリの懸念点とその対策

### 懸念点① テーマカラー変更による視認性低下とスタイル破綻

- **何が問題になりそうか**: テーマカラーをユーザーが自由に変更できるようにすると、選んだ色によって背景と同化して文字が読みにくくなったり（視認性の低下）、CSS設計が肥大化して画面表示が崩れる恐れがある。
- **なぜそう思うか**: 自由なカラーコード入力を許可すると、背景と同じ色や彩度・明度の極端な色が指定されるケースをすべて防ぐのが困難なため。
- **対策**: 自由入力（カラーピッカー）は採用せず、Excelのテーマカラーパレットのように、あらかじめ背景色やテキスト色とのコントラスト比（可読性）を検証・担保した「厳選24色プリセット」から選ばせる方式にする。これにより、CSS変数を切り替えるだけのシンプルなコード設計でスタイルの破綻を防ぎ、どの色を選んでもスタイリッシュで見やすいデザインを両立する。

### 懸念点② 交換メモ機能における個人情報取り扱い・法的リスク

- **何が問題になりそうか**: グッズの交換・譲渡メモ機能を設けた際、取引相手の住所・氏名などの個人情報が登録されて漏洩するリスクや、売買の仲介サービスと誤認されてプラットフォーム責任を問われるリスクがある。
- **なぜそう思うか**: 郵送交換では一時的に相手の送付先を扱うためメモ欄に貼り付けたくなる心理が働き、また金銭や物品のやり取りには法的な線引きが必要なため。
- **対策**: 住所や本名を入力するフォームは一切設けず、「相手のSNS表示名（@ID等）」と「取引進捗（送った/届いた）」のドロップダウン選択のみに機能を限定する。利用規約およびUI上に「個人情報は入力禁止」「金銭売買の仲介は行わない純粋な個人用メモ機能である」旨を明記する。

### 懸念点③ 外部サイトOGPスクレイピングの不安定性

- **何が問題になりそうか**: 本リリースで予定しているURL貼り付けによるOGP自動取得において、サイト側の仕様（OGP未設定、動的レンダリング、スクレイピング制限等）により情報取得に失敗し、ユーザー体験を損なう恐れがある。
- **なぜそう思うか**: 各ECサイトやSNSによってHTML構造やOGPの記述形式が統一されていないため。
- **対策**: OGP取得失敗を前提としたフォールバック設計を導入する。取得に失敗した場合はエラー画面を出さず、「手動入力モード」へシームレスにフォームを開き、ユーザー自身でタイトルや画像を登録できるようにする。

## 9. 今後の展開・発展の方向性

**機能追加の方向性**

- 通販サイトのURLを貼るだけで、タイトルや画像を自動抽出するOGPスクレイピング補完機能。
- X（旧Twitter）交換募集文ジェネレーター（【譲】【求】を選択して募集用ポスト文面を1クリック生成）。

**UI・体験の改善**

- 『ペルソナ3』風（クールなブルー・ガラス質感）や『ペルソナ5』風（エッジの効いた斜線・幾何学コントラスト）など、全体のUIトーンをプリセットから選べるスキン切り替え。
- Stimulusを活用した、チェック時の滑らかな完了演出アニメーション。

**機能以外の工夫**

- 痛バ（痛バッグ）を組む際の必要個数シミュレーター（A4サイズ＝缶バッジ24個など）のプリセット提案。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

| 項目 | 技術 |
| --- | --- |
| フレームワーク | Ruby on Rails 8（8.1.3 / Hotwire: Turbo Frames, Turbo Streams, Stimulus） |
| 認証 | Rails 8標準認証機能（`bin/rails generate authentication`） |
| フロントエンド / CSS | Tailwind CSS（tailwindcss-rails） |
| データベース | PostgreSQL |
| ストレージ | AWS S3（Active Storage経由でグッズ・アイコン画像を保存） |
| テスト | RSpec |
| デプロイ先 | Render |

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| **Ruby on Rails 8** | 採用 | 最新のRails 8標準認証機能（`generate authentication`）により、devise等の外部gemに頼らずシンプルでセキュアな個別認証を素早く構築できるため。また、Hotwireとの統合環境でSPAライクな滑らかな挙動をMPAベースで実現できるため。 |
| **Hotwire (Turbo + Stimulus)** | 採用 | 画面全体のリロードを挟まない滑らかさをRails標準の仕組みで最速構築できるため。Stimulusで「チェック時の完了演出」「アイコンタップ時の弾み」「一括削除時の震え演出」など、軽量なコードでアプリらしい手触りを実現できる。 |
| React / Vue (SPA) | 不採用（MVP時点） | 画面の滑らかさは魅力だが、MVPの段階でAPI分離や状態管理を導入するとキャッチアップ工数が肥大化し、リリースの遅延リスクが高いため。まずはHotwireで検証し、本リリース以降の選択肢とする。 |
| **PostgreSQL** | 採用 | Render等のPaaS環境でフルマネージドサービスとして標準提供されており、接続設定やバックアップが容易なため。また、複数ユーザーの同時アクセス・書き込みへの耐性に優れ、自社開発企業での採用実績も豊富なため。 |
| SQLite | 不採用 | Rails 8では本番運用の思想が強化されているものの、Renderなどの一般的なコンテナ型PaaSでは永続ディスク（Persistent Disk）のマウント設定やコストが別途発生し、運用の手間が増えるため。 |
| **Tailwind CSS + CSS変数** | 採用 | tailwindcss-railsを導入し、24色のテーマカラー切り替えをCSSカスタムプロパティで一元管理することで、ペルソナ風の幾何学的でスタイリッシュなデザインを破綻なくスピーディーに構築できるため。 |

**今回チャレンジしたい点**

- **Rails 8標準認証の実装**: 外部gemに依存せず、Rails 8の最新組み込み認証の構造を理解して堅牢なマルチユーザー環境を構築する。
- **Hotwire（Turbo/Stimulus）によるネイティブアプリ風UX**: 「アイコンが弾む」「チェック時に行が滑らかに遷移する」といったマイクロインタラクションをStimulusで実装する。
- **CSS変数とTailwind CSSによる動的テーマ切り替え**: 厳選24色のテーマパレットをCSS変数1つでアプリ全体に反映させる設計。

**不安な点**

- CSSアニメーションやStimulusのイベント発火を多用した際の、スマホ実機ブラウザでの描画パフォーマンスの低下やタップ遅延。

### 10-3. キャッチアップ不足の懸念とテスト方針

**キャッチアップ懸念への対策**
フロントエンドを最初からReact等のSPAにせず、Rails 8標準のHotwire（Turbo/Stimulus）を徹底活用することで、学習コストによる工数遅延を回避する。

**テスト方針（RSpec）**

- モデルスペック（グッズ登録時のバリデーション、ステータス変更ロジック、個数計算）を重点的に記述し、データの整合性を担保する。
- システムスペック（ログインから推し登録、グッズの追加・チェックボックス更新・一括削除までの一連の重要フロー）を最低限カバーし、リリース時のデグレを防ぐ。
